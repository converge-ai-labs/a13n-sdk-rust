# Rust SDK and CLI Contracts

## Authority and ownership

The `a13n` crate and separately versioned `a13n-service-cli` consume the exact local Service snapshot in `contract/source.json`. Service owns authorization, durable state and protocol semantics; neither generation nor local tests require its source checkout. Before 0.1.0, obsolete SDK or CLI call shapes are not retained through compatibility aliases, shims or protocol fallbacks. Optional fields and cursor-only observation remain supported as part of the current pinned Service contract. The Rust SDK owns its native interaction workflow and generated operation adapters, not a second Service scheduler.

Every pinned OpenAPI operation is available through `Client::execute` and the generated typed `Client::api()` graph, sharing one transport, authentication and wire models. `client.api().agents()` is the canonical native Service API entry; `client.agent(agent_id)` remains the authored workflow entry. The obsolete `Client::resources()` accessor is absent, with no compatibility alias; resource modules/types and borrowed lifetimes remain unchanged. Ordinary Agent invocation is a crafted layer over the generated Thread and inbox mutations. Generated resource references bind IDs/keys locally; no discovery, key-to-ID lookup or credential-authority expansion occurs. Model resources select **keys**; Agent, Skill and other resources select **IDs**. Service secret resources are absent. Session grouping does not make a Thread permanently owned by an Agent.

## Agent interaction and lifecycle

`Client::agent(agent_id)` binds an owned Agent handle locally. `Agent::start(input)` creates a Thread with its first message; `Agent::send(thread_id, input)` submits to an existing Thread using that Agent. `start_with(input, StartOptions)` and `send_with(thread_id, input, SendOptions)` expose every valid optional request field, with one `run_options` grouping. Strings become text; public `Input::parts` and text/JSON/URL/Asset constructors own discriminators without another schema hierarchy. Wire-backed RunOptions, RunConfiguration and Overrides builders expose every selectable field and arbitrary JSON maps; not calling a nullable builder omits its field, passing `None` explicitly sends null. Selected canonical nested types are root exports. `StartOptions.message_history` imports completed native Pydantic AI ModelMessage objects once; ordered `serde_json::Map` messages and order-preserving nested JSON retain object-key order through authored/native submissions; Thread readback omits imported history. Service owns validation; callers preserve submitted order when persisting intent. Calls return one finite Interaction for result-only, raw frames or text preview on one observer/reader.

The accepted receipt may have a null Run. Before yielding any Run-scoped frame or returning a result, the SDK polls the exact receipt Entry until `consumed` and binds its immutable `assigned_run_id`. Assignment alone is not incorporation; an assigned Entry may return to pending and a different Run may eventually consume it. Failed and withdrawn dispositions are typed `Error::Submission` values with their Entry snapshots, never unrelated Run successes. The SDK verifies Thread, Entry and exact Run identities; it never substitutes a latest/head Run or automatically follows a successor.

After incorporation, `Interaction::next` yields only delta/boundary and gap/reset hints attributed to the exact Run. It reuses the Thread SSE parser; a fixed poll schedule detects completion with idle/busy SSE or blocked headers. An SSE error does not prevent authoritative result readback unless explicitly closed. `RunOutcome` exposes status, full JSON output, optional string-only text, pending approvals/calls, failure, Thread/Run IDs, an exact Run command handle and explicitly named `http_response` evidence. Empty strings, false, zero, null and empty containers retain their values; no Items call is required for the final reply. Completed, waiting, failed and cancelled are distinct outcomes. Run Items is committed window readback. Items have required dense 1-based ordinals; `RunItemsGetOptions.before` (>=1) and `after` (>=0) are mutually exclusive, and `limit` defaults to 200 with maximum 500. Default reads preserve the newest limit plus the entire mutable tail, even beyond limit, and expose only `run`, `items` and `complete`. Neither recent nor historical windows establish stream progress or heal gaps. `complete` means Run sealed, not full history loaded. The SDK has no automatic full-history loader or generic cursor pager for Items. Generated recursive display continuation types are presentation state, not execution state. Gaps/resets remain explicit readback hints; the SDK does not invent a UI reducer.

`ThreadView.last_run_id` names the most recently sealed Run of any outcome. Failed and cancelled Runs retain continuation history through the nearest checkpoint while pausing automatic advancement. A new explicit normal message continues that history; the SDK performs no implicit retry, resume or fork. Explicit resume is only for the exact idle last waiting Run.

One frozen ObservationOptions deadline spans Entry queueing, exact Run reads, SSE attachment and in-flight observation. Defaults are 300 seconds and 500 ms polling; repeated iteration/result cannot reset the budget. An explicit absolute deadline also bounds mutation time: pre-dispatch expiry is MutationTimeout; after attempted dispatch it is an UnknownOutcome cause. Observation expiry is Timeout. A fresh recovered selector creates a new bounded local observer. Close/drop never interrupts remote work; a cached result remains readable after close, uncached result does not. No detached observation tasks, unbounded buffers, implicit approval or automatic remote interruption exist.

`Entry::observe(options)` recovers from `client.entry(thread_id, entry_id)` without I/O or a fabricated receipt. `Run::observe(options)` constructs the same finite Interaction bound to that exact Run; `Run::result(options)` delegates to its result-only path. There is no authored Run wait alias, latest pointer lookup or successor following. ReceiptEvidence distinguishes EntrySubmission, ResumeRunReceipt and RecoveredIdentity. Interaction identity includes known IDs and the chosen key; `Interaction.run` remains absent for a submitted/recovered Entry until consumed. A provisional receipt Run is only evidence. Exact Run selectors acquire their Thread identity through verified Run readback.

`Run::resume(answers)` / `resume_with(answers, ResumeOptions)` translate ONE ID-keyed public Answer map into BOTH required wire maps in ONE mutation and return the SAME Interaction bound to a distinct authoritative successor. Returned requires an explicit JSON value (null is valid); deny reasons preserve omitted/null/empty. Optional input is part of the immutable atomic resume intent. Service alone validates exact batch coverage, question results, referenced assets and resume eligibility. No Entry or response is fabricated. `Run::fork(agent_id, input, ForkOptions)` wraps the current wire fork operation and returns an Entry-origin Interaction for its new Thread. `Run::interrupt` alone explicitly stops remote execution.

Generated full-body Thread/inbox submissions return `Response<models::Submitted>` with no authored binding or wait behavior. Advanced callers can explicitly bind that receipt with `Submitted::bind(&client, response)` to obtain Thread/Entry and nullable initial Run references; its `observe(key, options)` enters the same consumed-Entry/exact-Run observer. This does not create another high-level streaming product. The generated raw Thread stream operation and advanced `ThreadStream::open(thread_resource, options)` owned parser remain available for the Thread-wide protocol. Advanced callers can supply paired `StreamOptions.run` and `position` from application-established progress; `after` carries an optional Redis seek hint, not display coverage. Without a coverage baseline the reader retains cursor-only behavior and does not infer a display position. The paired claim is wire-shape checked (canonical nonnegative decimal components of at most 20 digits); Thread ownership and latest-attempt validation remain Service-owned.

`applied_cursor()` and `applied_position()` acknowledge the prior frame only when the next `next()` poll starts after application processing. Close, drop and received frames do not acknowledge pending output. Coverage advances only for contiguous deltas of the claimed Run and attempt. Other Runs cannot advance it; a gap, reset, attempt change or missing sequence freezes advancement until the application explicitly reopens with application-established progress. Boundaries remain observable and cannot bridge holes. `GapSignal.position` preserves an optional/null recovery target, distinct from a Redis cursor. Missing or stale seek hints alone do not establish a gap when coverage is supplied; Service owns retained replay and filtering. The SDK neither reconstructs missed output nor automatically heals gaps or discards application state; attempts superseding provisional output require application readback.

`SessionStream::open(session_resource, SessionStreamOptions)` is an independent single-connection native reader. `SessionFrame` carries canonical typed ThreadState, RunSnapshot, Delta and Gap models from the pinned Session schema; shared HTTP models are reused after semantic agreement checks. Every connection starts with fresh snapshots, without SSE IDs, Last-Event-ID, cursors or automatic reconnect. Session snapshots have no protocol size bound; the default adds no extra frame-size limit and an explicit nonzero `max_frame_bytes` budget is optional. Unknown event names are ignored before JSON decoding; malformed known frames and known frames with IDs fail. Required nullable fields retain omission rejection and explicit null. `response()` retains HTTP status/headers, EOF/error closes the reader, and close/drop or Client shutdown ends local observation. Callers explicitly open a fresh reader after disconnect; snapshots may omit already sealed Runs. RunSnapshot `first` defines suffix replacement, continuation is presentation state, and `complete` seals one Run display rather than the Session. No display reducer or fragment assembler is introduced.

`Interaction::next_text` is a lazy string-chunk projection on the SAME mutable reader. It emits only root assistant string CONTENT matched to a trustworthy START, excluding child attribution and display:false. It retains at most eight active root message identities, no transcript. Gap/reset, missing or ambiguous start, bounded-state exhaustion, invalid relevant protocol and trustworthy outer per-attempt sequence discontinuity produce sticky typed PreviewInterrupted. Native/custom source coordinates and filtered foreign Runs never define sequence holes. Unknown unframed CUSTOM events stay raw and are ignored by preview. An unexcluded root `CUSTOM` named `a13n.stream.fragment` conservatively interrupts because its opaque data frames ORIGINAL CUSTOM JSON; this helper has no assembler or reliable inner relevance field. This is unsupported framing, not a claim of assistant text loss. Interruption stops projection but preserves still-open `result` and deliberate sequential raw access; Rust mutable borrowing prevents concurrent readers. No reducer, baseline repair or fragment assembly occurs. Final Run output remains authoritative.

High-level start/send/resume/fork choose one random key before dispatch when omitted and expose it on identity/evidence. Explicit keys remain authoritative. There are no automatic mutation retries. A dispatched mutation without reliable acknowledgement, including malformed accepted receipts, returns UnknownOutcome with the chosen key, safe operation/known IDs and original typed cause. Canonical structured Service rejection stays Api; a status-only/unstructured gateway response remains UnknownOutcome with actual HTTP status and original low-level cause; validation, request-build failures and pre-dispatch cancellation stay their original errors. Mutation transport deadlines and observation deadlines remain distinct. A dropped future cannot return a generated key; durable callers persist their own key and identical intent before sending.

## Run configuration, native media and provider authorization

`Overrides.lazy_environment` preserves omitted/null/false; Service defaults to lazy preparation. Setting false prepares frozen Environment instances before Harness entry, while execution connections still open on first use. A reserved Environment identity does not establish readiness. `Overrides.skill_sync` accepts the canonical `OverrideSkillSync` union backed by `SharedSkillSync` or `IsolatedSkillSync`; callers explicitly supply the mode discriminator. Service defaults to shared publication (`overwrite=true`, `cleanup=false`), and an isolated policy opts into immutable package reuse with `cache_count=128`; zero disables trimming. Overrides replace the whole policy. Shared cleanup may remove other Agents' conventional skill names, including all names for an empty selection. The SDK neither materializes skills nor assumes directory readiness.

`StartOptions.run_options`, `SendOptions.run_options` and generated `Message.options` expose the same wire RunOptions. Calling `.configuration(None)` sends null; not calling it omits configuration. `.configuration(Some(RunConfiguration::new()))` selects the complete empty snapshot, independently of Agent overrides. For new Runs omission/null selects Service defaults; steering an active (accepted or running) Run with omission/null retains its frozen snapshot. Explicit `{}` does not merge hidden defaults; `allowed_hosts: null` is unrestricted and `[]` denies all destinations. Namespaced `extensions` preserve arbitrary JSON, including false, zero, null, empty arrays and nested objects. The SDK does not normalize hosts, apply download/TLS policy or decide conflicts. A differing explicit steering value against an active (accepted or running) Run surfaces Service conflict `run_configuration_immutable` without retries or delivery rewrites. A waiting Run is sealed, not active: ordinary messages queue until explicit resume and do not trigger this active-Run configuration comparison. Explicit `next_run` selects a new snapshot; recovery, resume and children retain their inherited snapshot.

Native `MessagePayload` text, URL and Asset parts remain ordered. Generated Model characteristics preserve image/video/URL input policy fields and their omitted/null/value distinctions without SDK media preparation or defaults. Service/Harness owns acquisition, byte budgets and capability validation. Stream deltas use only raw `event` plus required nullable `item` (missing item is invalid); ItemRef ordinal/response_group/failure and typed memory_sources preserve omission, null and values. Memory sources describe automatic delivery evidence, not complete model citations or all explicit tool reads. They retain their native AG-UI event map, including unknown events, ordered structured tool-result content, media descriptors/metadata, nulls and `subagentRunId`. Finite Interaction identity is the outer Service `run_id`; an inner child `RUN_FINISHED` cannot seal the root. Native message/tool IDs alone do not identify the source across inline children. Run Items content retains child attribution; neither the SDK nor CLI flattens children or media into root text. Authored input CUSTOM events are display evidence, not execution authority or lossless media bytes.

Provider types and catalog channels are dynamically discovered from Service; there is no SDK-owned exhaustive vendor whitelist or MCP client. Model Provider authorization and discovery use only the generated resource graph: `authorize`, `authorization().get/callback/delete` and `models().get`. They share scoped transport, actual success status and nullable response fidelity. Hosted `browser_callback` requires an unconfined user login session; manual authorization remains available to workspace-write actors, including API keys. Clients follow returned `AuthorizationStart.method`; hosted callback origin/client configuration, token storage and provider policy remain Service/operator-owned. The SDK has no second OAuth flow or credential store and does not log callback codes or tokens.

Saved `Item.content_refs` retain field-keyed immutable references, preview, byte size, media type and truncation. `client.api().runs().at(run_id).contents().at(content_id).get(...)` reads one authorized value explicitly; JSON stays native and truncated oversized JSON may be a text prefix. References do not alter final Run output or trigger expansion. Session `message_authors` queries retain exact Entry attribution. Findings, finding analyses and finding-agent operations stay in the generated native graph; Service owns tracing-backend availability, evidence validation and conditional updates.

## Memory Spaces, execution queries and Computer evidence

Memory Spaces and standalone Memories have separate lifecycles. The generated `memory_spaces()` graph exposes configuration CRUD, organization status/history/request and attached Sessions. A manual organization request returns `202 SpaceOrganizationStatus`, not an Interaction or completed Run. Service owns organization scheduling, thresholds, cooldown, execution authority and managed Memory storage. Files and revisions use the existing Memory graph through the Space's `memory_id`; that managed Memory cannot be mounted as a standalone Memory.

Session create/update accept optional nullable `memory`; settings preserve each provided `enabled` and `spaces` field. Omission/null on create leaves first successful business-Run acceptance to inherit Agent defaults. Explicit false disables participation; an explicit empty spaces list clears selection. PATCH merges provided settings fields, replaces an explicitly supplied spaces list, and treats outer null as no change. Readback defaults are observations, not caller intent. The labels helper sends labels only, preserving memory selection.

`RunView.memory_mounts` uses canonical `FrozenMemoryMount` as the lossless representation of the legacy/extended wire union: its shared required fields match `MemoryMount`, while optional `roots` and nullable `space_id` retain resolved scope. Missing roots remain absent, an empty list remains empty, and explicit null or malformed roots is rejected. Request `MemoryMount` stays independent and has no host-only roots or Space identity. Accepted roots and mount permission ceilings stay frozen across later Session/Thread edits.

Run list filters, executed Agent configuration, exact Attempt detail and usage metrics remain native queries. `RunAgent.revision` is the frozen revision and its `config` applies frozen Agent overrides; named models/connections/templates remain live. Attempt count and Attempt list length need not match. Required nullable timing fields preserve null independently of zero. Service computes speed over complete request duration, including first-chunk wait, and owns usage aggregation; clients do not derive billing from SSE timestamps or sealed snapshots.

An Environment mount's omitted permission ceiling retains legacy file/execution actions and grants no Computer actions. An explicit empty operations set grants none. The native Thread mount PATCH replaces the ceiling using the Thread ETag; already accepted Runs retain their snapshot. `computer().check(...)` is an explicit readiness query with checked/unsupported/not_ready results; it neither starts an Environment, captures an image nor grants input authority. Computer execution additionally requires the Agent toolset, exact action permissions and provider support/readiness.

Retained `content.tool_images` references preserve native metadata. `runs().at(run).images().at(image).get(...)` explicitly streams PNG/JPEG bytes with original headers, including no-store; it is separate from JSON/text `contents()`. Neither Items/events nor readiness checks automatically fetch screenshots. A display image reference is not a reusable Computer observation handle. Input unknown outcomes require reconciliation, never replay to repair display evidence.

`Overrides.builtin_skills` and `platform_tools` are independent selections with omitted/null/empty/value fidelity. Platform groups and read/write permissions stay typed; Service owns defaults and authorization. These options add no second facade, workflow, reducer or mutation retry.

## Desktop control, tool discovery and context usage

The native graph exposes all desktop-assistance operations and Run desktop-control GET/POST. `wait_reason=desktop_control` and `pending.desktop_control_id` retain their HTTP and Session projections. Desktop waiting ends an exact-Run finite Interaction normally; its raw HTTP result preserves pending control identity, including empty tool arrays. Metadata/viewing, request-control, input grants, disconnect, persisted completion and explicit Run resume have separate authority and completion boundaries. `preparing` is not input authority. Control/Completion `session_id` is a browser-session token, not a Service Session resource ID; epoch is nonnegative. The SDK performs no lease renew/reclaim, browser launch, completion or resume automatically. Completed stored user desktop-only control permits explicit empty answer maps when Service validates the checkpoint; agent assistance and other pending answers retain full atomic batch requirements.

Canonical `ToolSearch`, `ToolSearchConfig`, `NativeToolSearchConfig`, `ProxyToolSearchConfig` and `ToolSearchGroup` are shared across Agent configuration, Run overrides and Session projections. Closed new configuration objects reject unknown/cross-branch fields at typed deserialization. Required mode discriminators remain required; native strategy preserves omitted/null/value. ToolSearch optional config/groups are nonnullable when present. Run overrides replace the whole block; omitted/null retains revision and empty groups disables grouping. Source selection and numeric policy validation remain Service-owned; no SDK-owned search execution or legacy-field fallback exists.

`usage().context().get(...)` sends native thread/run/record selectors without duplicating Service's exactly-one-selector validation. Its successful body is `Option<ContextUsage>`; required nullable input/output/window fields preserve null and zero independently. It reports the eligible completed generation rather than a pending estimate or aggregate. No matching contribution returns JSON null; missing resources and malformed responses remain distinct errors. GET Run desktop-control is likewise nullable. Schema-derived nullable success annotations preserve `Option` through generated direct APIs, ordinary resources and CLI JSON output; nonnullable operations remain strict and empty/malformed JSON is not null.

## Wire, authentication and transport

Generated models preserve tagged unions, omitted/null/value distinctions and unknown extensible Run status values. `ModelConfigInput.settings` and `ModelConfigOutput.settings` preserve arbitrary native JSON values, including nested objects, arrays and null. Generated schemas retain 32-hex-digit Upload references and eight-character minimum passwords for bootstrap, change and reset; request forwarding does not duplicate Service policy enforcement. The SDK does not infer Service policy for model settings, extra-body/extra-headers replacement or provider affinity. `Response<T>` retains actual status, headers, ETag and request ID; conditional mutations take explicit preconditions. Cursor-bearing collections expose lazy `pages` without prefetch and reject repeated cursors. Binary success bodies stream without whole-body buffering, and uploads can own streaming bodies. Ordinary JSON/error bodies have a configurable default 16 MiB bound. Typed API, transport and protocol diagnostics redact raw secrets, URL and untrusted body text. Local timeout does not imply rollback or cancellation of durable work.

A bearer API key acts in its implicit workspace; no ordinary workspace ID or key argument is required for flat business routes. Session clients select a workspace via `.workspace(id)` and own cookie/CSRF state; this default header applies only to workspace-scoped operations. Explicit per-operation scope headers take precedence. Public, administrative and deployment-wide requests must not receive a session workspace header unless declared by the operation. Authorization remains Service-owned, including a key's inability to name another workspace. Client close cancels requests and releases the pool; there are no automatic write retries or redirects.

## CLI

The companion CLI has a complete generated static Clap catalogue with typed SDK dispatch for every pinned operation; `--schema`, `--example`, completion and help are offline. Generated commands coexist with ordinary `agents start`/`agents send --thread` helpers, `runs wait`/`runs result` and explicit Session/Thread event and inbox helpers. The Agent helpers accept either `--text` (including an empty string) or mutually exclusive `--payload` typed MessagePayload JSON. `--options` supplies complete typed RunOptions JSON; both JSON flags reuse inline JSON, `@file` and `@-` input, validation, timeout and cancellation. Configuration and nested false/empty values pass through unchanged. The Agent helpers delegate execution and waiting to the SDK; `--wait` emits acceptance and terminal outcome with original response metadata. Advanced Thread events remain Thread-wide, not a second ordinary finite-interaction API. `sessions events ID` emits typed fresh-snapshot JSONL with local close/timeout and no reconnect/cursor policy. The generated `sessions stream get` preserves raw bytes. `threads events --run ... --position ...` accepts paired application-established progress with optional `--after` seek hint; JSONL preserves optional gap targets and reports the prior applied position on cursor-bearing frames. The generated `threads stream get` forwards the corresponding query/header options and saves raw SSE without a reducer.

Flags/config profiles choose URL, optional scope for a login session or resource path, trusted CA and token **environment-variable name** (never token bytes). For API-key Agent use, no workspace flag is necessary. JSON default output preserves data/status/headers when requested; `--all` lazily fetches cursor pages. Unknown fields in known request models are locally rejected; this is not complete Service validation. Offline dry-run reports a redacted request plan without network or authorization claims. Binary downloads write to a same-directory temporary file and rename only after complete body/flush success; failures preserve an existing target and clean up the temporary file. Stdout frame output flushes before the next acknowledgement. CLI CAS and idempotency keys remain explicit; SDK-generated keys do not change these flags. Timeouts and Ctrl-C cancel local work only. The CLI has an independent workspace and release channel and is excluded from the SDK crate archive. The archive also excludes local `tmp/` scratch, logs and inspection copies; independently extracted consumers use only packaged SDK inputs.

## Verification boundaries

Operation coverage, typed wire models, metadata/auth/scope behavior, exact Entry/Run lifecycle, busy/idle SSE termination, cancellation, uploads/downloads, generated CLI dispatch and independent extracted-crate consumption require local tests. Optional disposable HTTPS Service acceptance checks integration with a particular snapshot, not provider production connectivity or publication. Source tests alone do not establish live compatibility.
