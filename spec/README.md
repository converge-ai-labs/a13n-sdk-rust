# Rust SDK and CLI Contracts

## Authority and ownership

The `a13n` crate and separately versioned `a13n-service-cli` consume the exact local Service snapshot in `contract/source.json`. Service owns authorization, durable state and protocol semantics; neither generation nor local tests require its source checkout. The Rust SDK owns its native interaction workflow and generated operation adapters, not a second Service scheduler.

All 225 pinned OpenAPI operations are available through `Client::execute` and the generated typed `Client::resources()` graph, sharing one transport, authentication and wire models. Ordinary Agent invocation is a crafted layer over the generated Thread and inbox mutations. Generated resource references bind IDs/keys locally; no discovery, key-to-ID lookup or credential-authority expansion occurs. Model resources select **keys**; Agent, Skill and other resources select **IDs**. Service secret resources are absent. Session grouping does not make a Thread permanently owned by an Agent.

## Agent interaction and lifecycle

`Client::agent(agent_id)` binds one Agent ID locally. `Agent::start(input, idempotency_key)` creates a Thread with the first message; `Agent::send(thread_id, input, idempotency_key)` submits a message to an existing Thread using the selected Agent. Input is text or a full typed `MessagePayload`; `start_with` and `send_with` accept typed complete optional request fields. Calls return one finite `Interaction`, exposing the canonical receipt, bound Thread, `next` frame iteration, `result` authoritative Run outcome and `close` local cleanup. There is no required intermediate observe factory and no separate high-level persistent Thread subscription.

The accepted receipt may have a null Run. Before yielding any Run-scoped frame or returning a result, the SDK polls the exact receipt Entry until `consumed` and binds its immutable `assigned_run_id`. Assignment alone is not incorporation; an assigned Entry may return to pending and a different Run may eventually consume it. Failed and withdrawn dispositions are typed `Error::Submission` values with their Entry snapshots, never unrelated Run successes. The SDK verifies Thread, Entry and exact Run identities; it never substitutes a latest/head Run or automatically follows a successor.

After incorporation, `Interaction::next` yields only delta/boundary and gap/reset hints attributed to the exact Run; unscoped changed hints and other Runs are not presented as this invocation's output. It reuses the existing typed Thread SSE parser; retained replay is not a lossless history. A fixed Run poll schedule stops finite iteration when the Run seals even if SSE is idle, busy with foreign frames or blocked on response headers. An SSE error is surfaced, and authoritative `result` remains available unless the interaction was explicitly closed. `result` need not connect SSE and returns `RunOutcome` with a bound exact Run, snapshot HTTP metadata, status, output, pending and failure. Completed, waiting, failed and cancelled are distinct terminal outcomes, not uniform success. Run Items is committed readback. Gaps/resets remain explicit readback hints; the SDK does not invent a UI reducer.

A single default 300-second deadline spans Entry queueing, Run execution, SSE connection and in-flight reads; default polling is 500 ms. Dropping a future cancels local observation, not remote execution. Closing or dropping an Interaction releases its local socket and never interrupts the Run. A cached result remains readable after close; uncached result after explicit close is an error. There are no detached observation tasks, unbounded buffers, hidden POST retries, implicit approval or automatic remote interruption. Caller-owned keys support explicit reconciliation after uncertain mutations. The authored `Run::wait` observes the exact Run to a terminal state; `Run::resume` with explicit answers and idempotency key returns a distinct bound successor with its receipt. `Run::interrupt` alone mutates remote execution.

Generated full-body Thread/inbox submissions return `Response<models::Submitted>` with no authored binding or wait behavior. Advanced callers can explicitly bind that receipt with `Submitted::bind(&client, response)` to obtain Thread/Entry and nullable initial Run references; its `wait` shares the consumed-Entry/exact-Run logic. This does not create another high-level streaming product. The generated raw Thread stream operation and advanced `ThreadStream::open(thread_resource, options)` parser remain available for the Thread-wide protocol, with bounded reconnects, applied cursors and authoritative readback responsibility.

## Wire, authentication and transport

Generated models preserve tagged unions, omitted/null/value distinctions and unknown extensible Run status values. The SDK does not infer Service policy for model settings, extra-body/extra-headers replacement or provider affinity. `Response<T>` retains actual status, headers, ETag and request ID; conditional mutations take explicit preconditions. Cursor-bearing collections expose lazy `pages` without prefetch and reject repeated cursors. Binary success bodies stream without whole-body buffering, and uploads can own streaming bodies. Ordinary JSON/error bodies have a configurable default 16 MiB bound. Typed API, transport and protocol diagnostics redact raw secrets, URL and untrusted body text. Local timeout does not imply rollback or cancellation of durable work.

A bearer API key acts in its implicit workspace; no ordinary workspace ID or key argument is required for flat business routes. Session clients select a workspace via `.workspace(id)` and own cookie/CSRF state; this default header applies only to workspace-scoped operations. Explicit per-operation scope headers take precedence. Public, administrative and deployment-wide requests must not receive a session workspace header unless declared by the operation. Authorization remains Service-owned, including a key's inability to name another workspace. Client close cancels requests and releases the pool; there are no automatic write retries or redirects.

## CLI

The companion CLI has a complete generated static Clap catalogue with typed SDK dispatch for every pinned operation; `--schema`, `--example`, completion and help are offline. Generated commands coexist with ordinary `agents start`/`agents send --thread` helpers, `runs wait`/`runs result` and explicit Thread event/inbox helpers. The Agent helpers delegate execution and waiting to the SDK; `--wait` emits acceptance and terminal outcome with original response metadata. Advanced Thread events remain Thread-wide, not a second ordinary finite-interaction API.

Flags/config profiles choose URL, optional scope for a login session or resource path, trusted CA and token **environment-variable name** (never token bytes). For API-key Agent use, no workspace flag is necessary. JSON default output preserves data/status/headers when requested; `--all` lazily fetches cursor pages. Unknown fields in known request models are locally rejected; this is not complete Service validation. Offline dry-run reports a redacted request plan without network or authorization claims. Binary downloads write to a same-directory temporary file and rename only after complete body/flush success; failures preserve an existing target and clean up the temporary file. Stdout frame output flushes before the next acknowledgement. Explicit CAS and idempotency keys are never inferred. Timeouts and Ctrl-C cancel local work only. The CLI has an independent workspace and release channel and is excluded from the SDK crate archive.

## Verification boundaries

Operation coverage, typed wire models, metadata/auth/scope behavior, exact Entry/Run lifecycle, busy/idle SSE termination, cancellation, uploads/downloads, generated CLI dispatch and independent extracted-crate consumption require local tests. Optional disposable HTTPS Service acceptance checks integration with a particular snapshot, not provider production connectivity or publication. Source tests alone do not establish live compatibility.
