# Rust SDK and CLI Contracts

## Authority and ownership

The `a13n` crate and separately versioned `a13n-service-cli` consume the exact local Service snapshot in `contract/source.json`. Service owns authorization, durable state and protocol semantics; neither generation nor local tests require its source checkout. Before 0.1.0, obsolete SDK or CLI call shapes are not retained through compatibility aliases, shims or protocol fallbacks. Optional fields and cursor-only observation remain supported as part of the current pinned Service contract. The Rust SDK owns its native interaction workflow and generated operation adapters, not a second Service scheduler.

Every pinned OpenAPI operation is available through `Client::execute` and the generated typed `Client::resources()` graph, sharing one transport, authentication and wire models. Ordinary Agent invocation is a crafted layer over the generated Thread and inbox mutations. Generated resource references bind IDs/keys locally; no discovery, key-to-ID lookup or credential-authority expansion occurs. Model resources select **keys**; Agent, Skill and other resources select **IDs**. Service secret resources are absent. Session grouping does not make a Thread permanently owned by an Agent.

## Agent interaction and lifecycle

`Client::agent(agent_id)` binds one Agent ID locally. `Agent::start(input, idempotency_key)` creates a Thread with the first message; `Agent::send(thread_id, input, idempotency_key)` submits a message to an existing Thread using the selected Agent. Input is text or a full typed `MessagePayload`; `start_with` and `send_with` accept typed complete optional request fields. `StartOptions.message_history` passes an initial list of native Pydantic AI ModelMessage JSON objects into `NewThread.message_history` only. The Service validates completed conversation content, size and closed tool-call/result pairing; the SDK neither invents a second message hierarchy nor reseeds history on follow-up. The immutable submitted JSON remains available in Thread readback. Calls return one finite `Interaction`, exposing the canonical receipt, bound Thread, `next` frame iteration, `result` authoritative Run outcome and `close` local cleanup. There is no required intermediate observe factory and no separate high-level persistent Thread subscription.

The accepted receipt may have a null Run. Before yielding any Run-scoped frame or returning a result, the SDK polls the exact receipt Entry until `consumed` and binds its immutable `assigned_run_id`. Assignment alone is not incorporation; an assigned Entry may return to pending and a different Run may eventually consume it. Failed and withdrawn dispositions are typed `Error::Submission` values with their Entry snapshots, never unrelated Run successes. The SDK verifies Thread, Entry and exact Run identities; it never substitutes a latest/head Run or automatically follows a successor.

After incorporation, `Interaction::next` yields only delta/boundary and gap/reset hints attributed to the exact Run; unscoped changed hints and other Runs are not presented as this invocation's output. It reuses the existing typed Thread SSE parser; retained replay is not a lossless history. A fixed Run poll schedule stops finite iteration when the Run seals even if SSE is idle, busy with foreign frames or blocked on response headers. An SSE error is surfaced, and authoritative `result` remains available unless the interaction was explicitly closed. `result` need not connect SSE and returns `RunOutcome` with a bound exact Run, snapshot HTTP metadata, status, output, pending and failure. Completed, waiting, failed and cancelled are distinct terminal outcomes, not uniform success. Run Items is committed window readback. Items have required dense 1-based ordinals; `RunItemsGetOptions.before` (>=1) and `after` (>=0) are mutually exclusive, and `limit` defaults to 200 with maximum 500. Default reads preserve the newest limit plus the entire mutable tail, even beyond limit, and have `baseline=true`. Explicit historical windows have `baseline=false` and null continuation/position/resume hint; they cannot seed live coverage, heal gaps or seal a live consumer. `complete` means Run sealed, not full history loaded. The SDK has no automatic full-history loader or generic cursor pager for Items. Generated recursive display continuation types are presentation state, not execution state. Gaps/resets remain explicit readback hints; the SDK does not invent a UI reducer.

`ThreadView.last_run_id` names the most recently sealed Run of any outcome. Failed and cancelled Runs retain continuation history through the nearest checkpoint while pausing automatic advancement. A new explicit normal message continues that history; the SDK performs no implicit retry, resume or fork. Explicit resume is only for the exact idle last waiting Run.

A single default 300-second deadline spans Entry queueing, Run execution, SSE connection and in-flight reads; default polling is 500 ms. Dropping a future cancels local observation, not remote execution. Closing or dropping an Interaction releases its local socket and never interrupts the Run. A cached result remains readable after close; uncached result after explicit close is an error. There are no detached observation tasks, unbounded buffers, hidden POST retries, implicit approval or automatic remote interruption. Caller-owned keys support explicit reconciliation after uncertain mutations. The authored `Run::wait` observes the exact Run to a terminal state; `Run::resume(&models::Resume, idempotency_key)` submits complete typed `approvals` and `calls` maps and optional `input: MessagePayload` in one atomic request, returning a distinct bound successor with its receipt. The Service requires exact pending coverage, validates question results and any referenced assets, and never treats input as a substitute for a result. Ordinary messages cannot close a wait. `Run::interrupt` alone mutates remote execution.

Generated full-body Thread/inbox submissions return `Response<models::Submitted>` with no authored binding or wait behavior. Advanced callers can explicitly bind that receipt with `Submitted::bind(&client, response)` to obtain Thread/Entry and nullable initial Run references; its `wait` shares the consumed-Entry/exact-Run logic. This does not create another high-level streaming product. The generated raw Thread stream operation and advanced `ThreadStream::open(thread_resource, options)` parser remain available for the Thread-wide protocol. Advanced callers can supply paired `StreamOptions.run` and `position` from an applied Run Items display; `after` carries its optional `resume_after` Redis seek hint, not display coverage. Without a coverage baseline the reader retains cursor-only behavior and does not infer a display position. The paired claim is wire-shape checked (canonical nonnegative decimal components of at most 20 digits); Thread ownership and latest-attempt validation remain Service-owned.

`applied_cursor()` and `applied_position()` acknowledge the prior frame only when the next `next()` poll starts after application processing. Close, drop and received frames do not acknowledge pending output. Coverage advances only for contiguous deltas of the claimed Run and attempt. Other Runs cannot advance it; a gap, reset, attempt change or missing sequence freezes advancement until the application explicitly reopens from covering Run Items. Boundaries remain observable and cannot bridge holes. `GapSignal.position` preserves an optional/null recovery target, distinct from a Redis cursor. Missing or stale seek hints alone do not establish a gap when coverage is supplied; Service owns retained replay and filtering. The SDK neither reconstructs missed output nor automatically heals gaps or discards application state; attempts superseding provisional output require application readback.

## Run configuration, native media and provider authorization

`StartOptions.options`, `SendOptions.options` and generated `Message.options` expose the same `RunOptionsInput.configuration`. `None` omits configuration, `Some(None)` sends null, and `Some(Some(Box<RunConfigurationInput>))` sends an entire snapshot, independently of Agent revision overrides. For new Runs omission/null selects Service defaults; steering an active (accepted or running) Run with omission/null retains its frozen snapshot. Explicit `{}` does not merge hidden defaults; `allowed_hosts: null` is unrestricted and `[]` denies all destinations. Namespaced `extensions` preserve arbitrary JSON, including false, zero, null, empty arrays and nested objects. The SDK does not normalize hosts, apply download/TLS policy or decide conflicts. A differing explicit steering value against an active (accepted or running) Run surfaces Service conflict `run_configuration_immutable` without retries or delivery rewrites. A waiting Run is sealed, not active: ordinary messages queue until explicit resume and do not trigger this active-Run configuration comparison. Explicit `next_run` selects a new snapshot; recovery, resume and children retain their inherited snapshot.

Native `MessagePayload` text, URL and Asset parts remain ordered. Generated Model characteristics preserve image/video/URL input policy fields and their omitted/null/value distinctions without SDK media preparation or defaults. Service/Harness owns acquisition, byte budgets and capability validation. Stream deltas use only raw `event` plus required nullable `item` (missing item is invalid); ItemRef ordinal/response_group/failure preserve omission, null and arbitrary JSON values. They retain their native AG-UI event map, including unknown events, ordered structured tool-result content, media descriptors/metadata, nulls and `subagentRunId`. Finite Interaction identity is the outer Service `run_id`; an inner child `RUN_FINISHED` cannot seal the root. Native message/tool IDs alone do not identify the source across inline children. Run Items content retains child attribution; neither the SDK nor CLI flattens children or media into root text. Authored input CUSTOM events are display evidence, not execution authority or lossless media bytes.

Provider types and catalog channels are dynamically discovered from Service; there is no SDK-owned exhaustive vendor whitelist or MCP client. Model Provider authorization and discovery use only the generated resource graph: `authorize`, `authorization().get/callback/delete` and `models().get`. They share scoped transport, actual success status and nullable response fidelity. Hosted `browser_callback` requires an unconfined user login session; manual authorization remains available to workspace-write actors, including API keys. Clients follow returned `AuthorizationStart.method`; hosted callback origin/client configuration, token storage and provider policy remain Service/operator-owned. The SDK has no second OAuth flow or credential store and does not log callback codes or tokens.

## Wire, authentication and transport

Generated models preserve tagged unions, omitted/null/value distinctions and unknown extensible Run status values. `ModelConfigInput.settings` and `ModelConfigOutput.settings` preserve arbitrary native JSON values, including nested objects, arrays and null. Generated schemas retain 32-hex-digit Upload references and eight-character minimum passwords for bootstrap, change and reset; request forwarding does not duplicate Service policy enforcement. The SDK does not infer Service policy for model settings, extra-body/extra-headers replacement or provider affinity. `Response<T>` retains actual status, headers, ETag and request ID; conditional mutations take explicit preconditions. Cursor-bearing collections expose lazy `pages` without prefetch and reject repeated cursors. Binary success bodies stream without whole-body buffering, and uploads can own streaming bodies. Ordinary JSON/error bodies have a configurable default 16 MiB bound. Typed API, transport and protocol diagnostics redact raw secrets, URL and untrusted body text. Local timeout does not imply rollback or cancellation of durable work.

A bearer API key acts in its implicit workspace; no ordinary workspace ID or key argument is required for flat business routes. Session clients select a workspace via `.workspace(id)` and own cookie/CSRF state; this default header applies only to workspace-scoped operations. Explicit per-operation scope headers take precedence. Public, administrative and deployment-wide requests must not receive a session workspace header unless declared by the operation. Authorization remains Service-owned, including a key's inability to name another workspace. Client close cancels requests and releases the pool; there are no automatic write retries or redirects.

## CLI

The companion CLI has a complete generated static Clap catalogue with typed SDK dispatch for every pinned operation; `--schema`, `--example`, completion and help are offline. Generated commands coexist with ordinary `agents start`/`agents send --thread` helpers, `runs wait`/`runs result` and explicit Thread event/inbox helpers. The Agent helpers accept either `--text` (including an empty string) or mutually exclusive `--payload` typed MessagePayload JSON. `--options` supplies complete typed RunOptions JSON; both JSON flags reuse inline JSON, `@file` and `@-` input, validation, timeout and cancellation. Configuration and nested false/empty values pass through unchanged. The Agent helpers delegate execution and waiting to the SDK; `--wait` emits acceptance and terminal outcome with original response metadata. Advanced Thread events remain Thread-wide, not a second ordinary finite-interaction API. `threads events --run ... --position ...` accepts a paired applied display baseline with optional `--after` seek hint; JSONL preserves optional gap targets and reports the prior applied position on cursor-bearing frames. The generated `threads stream get` forwards the corresponding query/header options and saves raw SSE without a reducer.

Flags/config profiles choose URL, optional scope for a login session or resource path, trusted CA and token **environment-variable name** (never token bytes). For API-key Agent use, no workspace flag is necessary. JSON default output preserves data/status/headers when requested; `--all` lazily fetches cursor pages. Unknown fields in known request models are locally rejected; this is not complete Service validation. Offline dry-run reports a redacted request plan without network or authorization claims. Binary downloads write to a same-directory temporary file and rename only after complete body/flush success; failures preserve an existing target and clean up the temporary file. Stdout frame output flushes before the next acknowledgement. Explicit CAS and idempotency keys are never inferred. Timeouts and Ctrl-C cancel local work only. The CLI has an independent workspace and release channel and is excluded from the SDK crate archive. The archive also excludes local `tmp/` scratch, logs and inspection copies; independently extracted consumers use only packaged SDK inputs.

## Verification boundaries

Operation coverage, typed wire models, metadata/auth/scope behavior, exact Entry/Run lifecycle, busy/idle SSE termination, cancellation, uploads/downloads, generated CLI dispatch and independent extracted-crate consumption require local tests. Optional disposable HTTPS Service acceptance checks integration with a particular snapshot, not provider production connectivity or publication. Source tests alone do not establish live compatibility.
